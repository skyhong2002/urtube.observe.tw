# SEO / GSC handoff (GSC-20261023)

Scope: `https://urtube.observe.tw/`. Codex owns Search Console (property,
sitemap submission, URL inspection). This document records the code side:
diagnosis, the minimal fixes, tests and deployment evidence. Submitting a
sitemap is not indexing, and nothing here guarantees Google will index a URL.

retest returned 200.

## Diagnosis (2026-10-23, read-only, on skyhong-SM)

Host: 13 of 15 GiB RAM used, 16 GiB swap in use, load ~27, IO pressure
`some avg60≈52–60%` (mostly other projects' MariaDB and Next.js servers).

`/robots.txt` and `/sitemap.xml` (public, via Cloudflare): 200. The sitemap is
well-formed (`xmllint`), with 50 `<loc>`: `/`, `/privacy`, and `/<handle>` +
`/<handle>/insights` for 24 public dashboards. Before this change it was served
with `Cache-Control: public, max-age=3600`.

Sequential anonymous loopback probes (Host `urtube.observe.tw`,
`X-Forwarded-Proto: https`, 60 s timeout): `/` timed out; the static
`/privacy` returned 200 only after 54 s; every profile page probed then also
timed out. A retry of `/` timed out at 180 s, after which `/healthz` timed out
too and Docker marked `urtube-app` unhealthy (15 consecutive failures). The Node
main thread was in `D` state (blocked on disk reads, no major faults) with
~0 CPU. It became healthy again a few minutes after `/` stopped being requested.

Cause: the landing page computed public community statistics synchronously on
the request thread: `youtubeChannelTotals('90d')` for every public archive,
cached for 5 minutes. Under IO pressure one cold computation took longer than
the cache lifetime, so each later homepage request started another. That
blocked every route, including health checks and the profile pages in the
sitemap. This matches "first homepage test timed out, retest 200" and is a
plausible reason Googlebot defers crawling (48 "Discovered"). It was the one
remaining synchronous archive scan on a public page after 6929385.

## Fixes

1. `src/youtube/community.ts`, `src/index.ts`: community statistics read
   channel totals through the existing read pool (`cachedChannelTotalsFor`).
   One refresh runs at a time; a request waits at most 2 s. After that it gets
   the last result **only if the set of public members is unchanged**;
   otherwise it gets the "unavailable" state with current public profiles. A
   member made private is never included in a served aggregate, including
   while a refresh is in flight. Failures still hide stale totals.
2. `/sitemap.xml`: `Cache-Control: no-cache` (was `public, max-age=3600`), so
   any cache must revalidate. The origin already listed only
   `dashboardPublic` users on every request; a dashboard made private now
   leaves the sitemap at once, without waiting out a cache's lifetime.

Unchanged: robots rules, canonical tags, `X-Robots-Tag: noindex` on private,
keyed, history and member pages, visibility rules, private-by-default signup,
and all processing and budgets.
