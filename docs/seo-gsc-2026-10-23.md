# SEO / GSC handoff (GSC-20261023)

Scope: `https://urtube.observe.tw/`. Codex owns Search Console (property,
sitemap submission, URL inspection). This document records the code side:
diagnosis, the minimal fixes, tests and deployment evidence. Submitting a
sitemap is not indexing, and nothing here guarantees Google will index a URL.

## Diagnosis (2026-10-23, read-only, on skyhong-SM)

Host: 13 of 15 GiB RAM used, 16 GiB swap in use, load ~27, IO pressure
`some avg60≈52–60%` (mostly other projects' MariaDB and Next.js servers).

`/robots.txt` and `/sitemap.xml` (public, via Cloudflare): 200. The sitemap is
well-formed (`xmllint`), with 50 `<loc>`: `/`, `/privacy`, and `/<handle>` +
`/<handle>/insights` for 24 public dashboards. Before this change it was served
with `Cache-Control: public, max-age=3600`.

Sequential anonymous loopback probes (Host `urtube.observe.tw`,
`X-Forwarded-Proto: https`, 60 s timeout): `/` timed out; the static
`/privacy` returned 200 only after 54 s; every profile page probed then also
timed out. A retry of `/` timed out at 180 s, after which `/healthz` timed out
too and Docker marked `urtube-app` unhealthy (15 consecutive failures). The Node
main thread was in `D` state (blocked on disk reads, no major faults) with
~0 CPU. It became healthy again a few minutes after `/` stopped being requested.

Cause: the landing page computed public community statistics synchronously on
the request thread: `youtubeChannelTotals('90d')` for every public archive,
cached for 5 minutes. Under IO pressure one cold computation took longer than
the cache lifetime, so each later homepage request started another. That
blocked every route, including health checks and the profile pages in the
sitemap. This matches "first homepage test timed out, retest 200" and is a
plausible reason Googlebot defers crawling (48 "Discovered"). It was the one
remaining synchronous archive scan on a public page after 6929385.

## Fixes

1. `src/youtube/community.ts`, `src/index.ts`: community statistics read
   channel totals through the existing read pool (`cachedChannelTotalsFor`).
   One refresh runs at a time; a request waits at most 2 s. After that it gets
   the last result **only if the set of public members is unchanged**;
   otherwise it gets the "unavailable" state with current public profiles. A
   member made private is never included in a served aggregate, including
   while a refresh is in flight. Failures still hide stale totals.
2. `/sitemap.xml`: `Cache-Control: no-cache` (was `public, max-age=3600`), so
   any cache must revalidate. The origin already listed only
   `dashboardPublic` users on every request; a dashboard made private now
   leaves the sitemap at once, without waiting out a cache's lifetime.

Unchanged: robots rules, canonical tags, `X-Robots-Tag: noindex` on private,
keyed, history and member pages, visibility rules, private-by-default signup,
and all processing and budgets.

## Part 2 — follow-up fix: Insights reference freshness off the request thread

Cause: every Insights render called `youtubeReferenceDataUpdatedAt()`
synchronously for each reference-population contributor (14 in production).
It is `MAX()` over `youtube_watch_events.imported_at`,
`youtube_videos.metadata_fetched_at`, `youtube_channels.metadata_fetched_at`
and `youtube_video_progress.observed_at`. The first two have no index
(`sqlite_master` has none), so each call reads those tables in full. With
archives up to 188 MB and a thin page cache, that blocked the request thread,
including `/healthz`. This was the remaining synchronous read on the Insights
path after 6929385 moved the channel totals to the pool.

Fix: `youtubeReferenceDataUpdatedAt` is added to the read pool's read-only
whitelist and read through `cachedReadAsync` (keyed by the archive's revision,
5-minute TTL, concurrent requests share one read). No permanent index is added
(AGENTS: main's TEMP-lookup approach supersedes a permanent index migration).
Visibility rules, timeouts and the reference-population semantics are
unchanged.

Tests: `npm run typecheck` pass; full suite 579 tests, 577 pass, 0 fail,
2 skipped (Python compute service). `tests/read-pool.test.ts` now checks the
pooled read equals the same read on the request thread.

## Open items

- **Insights latency.** Public Insights pages (24 of the 50 URLs) take
  ~20–40 s, and the largest archives exceed 90 s cold, under the host's current
  IO pressure (other projects' MariaDB/Next.js; swap ~16 GiB). They no longer
  block health or other pages, but Googlebot may time out on them. Making them
  fast needs a design change (for example precomputed or stale-while-revalidate
  Insights, or a larger pool), which is a backend change for the user to decide.
  Host memory and IO pressure are outside this project.
- **Identical meta description** on every page (generic site description).
  Not a blocker for indexing; per-profile descriptions would be a copy/SEO
  improvement.
- **`/api/youtube/recent.json`** (anonymous, 200) returns the default owner's
  10 most recent videos without watch times, because that owner's dashboard is
  public. This is existing, tested behavior (`tests/privacy.test.ts`); it is not
  in the sitemap. Changing it is an API-contract decision for the user.
- **No full 50-URL scan** has been run after the fixes. Only the samples above
  were checked, to avoid loading the host.
- Google indexing is not confirmed. GSC actions and their results belong to
  Codex; a sitemap submission or indexing request is not indexing.

## Part 4 — Insights latency (follow-up to the open item above)

Read-only diagnosis (2026-10-23 ~18:45 +08:00):

- **Every archive's revision changes every few minutes without content
  changes.** In a 120 s window, all 38 archives' `PRAGMA data_version` changed
  (94 changes; up to 7 in one archive). The writes were updates without row
  inserts: the worker writes `youtube_sync_state` (`worker_cycle_at`,
  `worker_stage`, …) for every user every cycle. Every revision-keyed
  `cachedReadAsync` entry was therefore invalid, and almost every public page
  view recomputed everything.
- **What a recompute costs**, timed on fresh read-only connections inside the
  app container (`nice -n 19`, timings only):
  - For `gwen85`, its own reads take ~6 s (dashboard 2.75 s cold / 2.28 s
    warm, crystal shifts 0.74 s). The **reference population** (14
    contributors' channel totals + freshness) took **27.7 s cold** and <1 s
    warm. The slowest contributor took 12 s cold and 0.23 s warm.
  - For `skyhong.tw` (largest), the own dashboard took **18 s cold / 4.9 s
    warm**.
  - "Cold" here is mostly disk: the page cache is ~1.4 GiB under swap.

Two minimal options:

- **A. Stale-while-revalidate for visitors other than the owner**, plus one
  start-up warm-up. A visitor who is not the owner gets the previous
  aggregates while one background recompute runs (the existing single-flight
  `cachedReadAsync`, `staleFor` = 24 h). The owner's own view keeps current
  data. After start, each public page is rendered once, one at a time, as an
  anonymous visitor.
- **B. Make the revision ignore bookkeeping writes.** This would mean changing
  the worker to skip unchanged sync-state writes (but `worker_cycle_at` changes
  every cycle by design), adding a content-version table, or running a
  COUNT/SUM content signature per request (itself a full scan when cold). That
  changes worker behavior or schema.

**Chosen: A.** It touches neither the worker nor the schema, reuses the
existing cache and pool, and adds no permanent index, no pool size or timeout
change, and no new periodic job. Privacy:

- Caches hold data, never authorization. `profileAccess` runs on every request
  and again after the Insights awaits, so a dashboard made private returns 404
  at once, even with warm caches.
- Reference contributors are listed fresh on every request, so a withdrawal
  takes effect immediately.
- Owner actions (Takeout import, profile change, deletion) already call
  `clearReadCaches()`.
- Nothing new is rendered: the same public projection, only possibly older
  (refreshed on the next visit).

The warm-up runs once, 120 s after start: about 50 page renders, one at a
time. That is the same work as the first visitors after a deploy, done before
they arrive.

Tests: typecheck pass. Full suite 581 tests, 579 pass, 0 fail, 2 skipped
(Python compute service). New tests: stale-while-revalidate semantics
(`tests/read-pool.test.ts`), and warm-up covering only public dashboards plus
a 404 after unpublishing despite warm caches (`tests/visibility.test.ts`).
Production acceptance for this change is reported in the GSC-20261023 thread,
so that recording a SHA does not trigger another docs-only deploy.

## Part 5 — cold-start cost and health pauses (second round)

Measurements on the production host (2026-10-23, one at a time, under the
shared build lock `/home/deck/.cache/observe-build-0.lock`):

- **What makes a read cold.** Every dashboard and channel-totals read first
  calls `ensureEstimatedEvents()`. That runs the content-key query
  (COUNT/SUM/MAX over `youtube_watch_events`, `youtube_videos`, progress) and
  then materializes the estimated-events TEMP table. Both read whole tables,
  including the wide `youtube_videos` rows:
  - the key query alone took 127.7 s over the 14 archives an Insights page
    reads, and up to 69.5 s for one archive;
  - one contributor's channel totals took 43.9 s cold and 0.46 s warm;
  - the largest account's own dashboard took 17.5 s cold and 3.8 s warm.

  The TEMP table lives in the connection's memory, so it is gone after every
  restart. It is also rebuilt at least every 5 minutes.
- **Ruled out as the cause of health pauses:**
  - write-lock waits: 477 `BEGIN IMMEDIATE; ROLLBACK` probes, p99 7.9 ms,
    max 349 ms;
  - main-thread CPU: deserializing pooled results took 259 ms in total, and
    `computeTagLean` for 14 contributors took 71 ms.
- **On 0175624**, one cold request ran for more than 120 s. During it,
  `/healthz` was sampled 109 times: 0 timeouts, max 0.99 s. The main thread
  showed swap-in bursts (the app process had ~250 MB swapped and ~41 MB
  resident).
- **The remaining timeouts** came while the process opened archives for the
  first time (just after start, and during the warm-up's sequential first
  opens). A write-mode `Repository` open runs the full-table
  `backfillYoutubeChannelIds()` UPDATE on the opening thread, which for the
  web server is the request thread.
- **The read pool has two threads.** While background recomputes held them,
  small reads on the request path (counts, metadata-processing) waited in
  the same queue.

Options:

- **Semantic revision** (key the caches on content instead of
  `data_version`). Not chosen: validating means running the same key query
  (up to 69.5 s cold), and a new process still has nothing cached.
- **Durable aggregates** (chosen). Each pooled aggregate read also writes its
  result to `<archive>.sqlite-aggregates/`. The file is keyed by the owner's
  user ID and the read key, and stores the import mark (`youtube_imports`
  count and latest time). Visitors other than the owner get, on a memory
  miss, the durable copy if it is younger than 24 h and no import happened
  since. A background refresh then runs, at most every 10 minutes per read.
  The request path no longer queues behind background recomputes, because
  counts and metadata-processing use the same mechanism.

Rules that still apply:

- The owner always computes current data and never reads a copy.
- Access, sessions, friendships and reference consent are checked after
  every read and immediately before rendering (8 regression tests).
- Account deletion removes the copies.
- A Takeout import in the app removes the user's copies. Any import (app or
  ingest) changes the import mark, so earlier copies are never used.
- A restore moves the default archive's copies aside along with it.
- The copies are not included in backups.
- The copies contain no decrypted data: the read threads have no data key.

The web server's `UserRegistry` also skips the open-time full-table channel
repair (`repairArchivesOnOpen = false`). The worker and ingest still run it
when they open archives, and every writer backfills the videos it touches.
The start-up warm-up waits for the read pool to go idle after each page.

No index, schema, worker, pool-size or timeout change. Tests: typecheck pass;
full suite 592 tests, 590 pass, 0 fail, 2 skipped (Python compute service).
New tests: durable copies are served after a restart (no file rewritten),
never to the owner, never to another account, and never across an import;
they are removed with the account, and a 404 follows unpublishing; the web
server opens archives without the repair. Production acceptance is recorded
in the GSC-20261023 thread.
